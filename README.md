# PetHome — Software Requirements Specification

เอกสารฉบับนี้เป็นข้อกำหนดซอฟต์แวร์ของ **PetHome** แพลตฟอร์มประกาศสัตว์เลี้ยงเพื่อหาบ้านใหม่และจัดการคำขอรับเลี้ยง โดยอ้างอิงการทำงานที่มีอยู่ใน source code ปัจจุบัน

เอกสารประกอบ:

- [คู่มือผู้ใช้](./USER_GUIDE.md) — การสมัครสมาชิก ค้นหา ลงประกาศ ส่งคำขอ และจัดการรายงาน
- [คู่มือผู้พัฒนา](./DEVELOPER_GUIDE.md) — การติดตั้ง โครงสร้างระบบ ฐานข้อมูล การทดสอบ และการ deploy

## 1. ภาพรวมเอกสาร

### 1.1 วัตถุประสงค์

PetHome ช่วยให้ผู้ที่ต้องการหาบ้านใหม่สามารถเผยแพร่ข้อมูลสัตว์เลี้ยง และช่วยให้ผู้สนใจรับเลี้ยงค้นหา ติดต่อ และส่งคำขอได้ในช่องทางเดียว เจ้าของประกาศใช้ระบบเพื่อคัดเลือกคำขอ ส่วนผู้ดูแลระบบใช้ตรวจสอบรายงานประกาศที่ไม่เหมาะสม

### 1.2 ขอบเขตระบบ

**อยู่ในขอบเขต**

- เว็บไซต์แบบ server-rendered ด้วย Flask และ Jinja2
- บัญชีผู้ใช้สองบทบาท: `user` และ `admin`
- ประกาศสุนัขหรือแมว พร้อมข้อมูลพื้นฐาน รูปภาพ และสถานะ
- ค้นหา/กรองประกาศที่ยังพร้อมหาบ้าน พร้อม pagination 12 รายการต่อหน้า
- คำขอรับเลี้ยงแบบไม่บังคับ login
- เจ้าของประกาศดู อนุมัติ หรือปฏิเสธคำขอ
- รายงานประกาศและการจัดการโดยผู้ดูแลระบบ
- การแจ้งเตือนผ่าน Resend Email API เมื่อกำหนดค่าไว้

**อยู่นอกขอบเขตของรุ่นปัจจุบัน**

- แชตภายในระบบ การชำระเงิน และการนัดหมาย
- การยืนยันตัวตนผู้ใช้ด้วยอีเมล/OTP
- การรับรองความถูกต้องของข้อมูลสัตว์โดยเจ้าหน้าที่ก่อนเผยแพร่
- การแก้ไขข้อมูลคำขอรับเลี้ยงโดยผู้สมัคร
- การอัปโหลดหลายรูปต่อประกาศผ่านหน้าเว็บ (schema รองรับ `pet_images` แต่หน้าเว็บปัจจุบันใช้รูปหลักหนึ่งรูป)

### 1.3 ผู้มีส่วนได้ส่วนเสียและบทบาท

| บทบาท | ความรับผิดชอบ |
|---|---|
| ผู้เยี่ยมชม | ดูและค้นหาประกาศ ส่งคำขอรับเลี้ยงโดยกรอกข้อมูลติดต่อ |
| ผู้ใช้/เจ้าของประกาศ | สมัครและเข้าสู่ระบบ ลงประกาศ แก้ไข/ลบประกาศ ดูและจัดการคำขอ |
| ผู้ดูแลระบบ | ตรวจสอบรายงาน ดำเนินการกับรายงาน ปิดประกาศที่มีปัญหา |
| ผู้ดูแลระบบโครงสร้างพื้นฐาน | ตั้งค่า environment, MySQL, Cloudinary, Resend และ deploy |

## 2. คำศัพท์และสถานะ

| คำศัพท์ | ความหมาย |
|---|---|
| ประกาศ | ข้อมูลสัตว์หนึ่งรายการในตาราง `pets` |
| เจ้าของประกาศ | ผู้ใช้ที่สร้างประกาศ ไม่จำเป็นต้องเป็นเจ้าของสัตว์ตามกฎหมาย |
| คำขอ | รายการความประสงค์รับเลี้ยงใน `adoption_requests` |
| สถานะประกาศ | `available`, `adopted`, `rejected` |
| สถานะคำขอ | `pending`, `approved`, `rejected`, `cancelled` |
| สถานะรายงาน | `pending`, `reviewed`, `dismissed` |

## 3. ข้อกำหนดการทำงาน (Functional Requirements)

### FR-01 บัญชีและการเข้าถึง

1. ผู้ใช้ต้องสมัครด้วยชื่อ อีเมล และรหัสผ่าน
2. อีเมลต้องไม่ซ้ำใน `users`
3. ระบบต้องเก็บรหัสผ่านเป็น hash ด้วย Werkzeug ไม่เก็บ plaintext
4. การเข้าสู่ระบบต้องสร้าง session ที่มี `user_id`, `user_name` และ `role`
5. ผู้ใช้ logout ผ่านคำขอ `POST` และ session ต้องถูกล้าง
6. ฟังก์ชันที่ต้องมีสิทธิ์ใช้ต้องตรวจ session; หน้าผู้ดูแลต้องตรวจ `role=admin`

### FR-02 ค้นหาและดูประกาศ

1. หน้าหลักแสดงเฉพาะประกาศสถานะ `available`
2. ผู้ใช้กรองได้ด้วยประเภท จังหวัด คำค้น ชื่อ/พันธุ์/รายละเอียด เพศ ช่วงอายุ ทำหมัน และวัคซีน
3. ระบบเรียงประกาศใหม่ไปเก่า และแบ่งหน้า หน้าละ 12 รายการ
4. หน้ารายละเอียดต้องแสดงชื่อ ประเภท พันธุ์ เพศ อายุ จังหวัด สถานะทำหมัน วัคซีน คำอธิบาย เจ้าของ และรูปหลักถ้ามี

### FR-03 จัดการประกาศ

1. ผู้ใช้ที่ login แล้วเพิ่มประกาศได้เฉพาะ `หมา` หรือ `แมว`
2. ต้องระบุชื่อ เพศ อายุ จังหวัด คำอธิบาย และยืนยันว่าข้อมูลเป็นความจริง
3. อายุรับเป็นปี 0–30 และเดือน 0–11 แล้วจัดเก็บเป็น `age_months`
4. จังหวัดต้องเป็นหนึ่งในรายการจังหวัดที่กำหนดใน backend
5. รูปที่อัปโหลดต้องเป็น PNG/JPG/JPEG/GIF และ request รวมต้องไม่เกิน 5 MB
6. รูปถูกส่งไป Cloudinary เมื่อกำหนดค่า Cloudinary ครบ มิฉะนั้นเก็บใน `frontend/static/uploads`
7. เจ้าของประกาศแก้ไขและลบเฉพาะประกาศของตนเอง
8. การลบประกาศต้องลบคำขอที่เกี่ยวข้องก่อน และข้อมูลรูปจะถูกลบตาม foreign key

### FR-04 คำขอรับเลี้ยง

1. ผู้สนใจส่งคำขอจากหน้ารายละเอียดโดยไม่ต้อง login
2. ต้องระบุชื่อและโทรศัพท์; อีเมล จังหวัด อาชีพ ประสบการณ์ ลักษณะที่พัก สมาชิกในบ้าน และข้อความเป็นข้อมูลเสริม
3. ระบบสร้างหรือปรับปรุงผู้สมัครใน `users`; ถ้าไม่มีอีเมลจะสร้างอีเมลภายในรูปแบบ `guest-...@pethome.local`
4. ผู้สมัครหนึ่งคนส่งคำขอซ้ำต่อสัตว์หนึ่งตัวไม่ได้
5. ห้ามส่งคำขอให้ประกาศของตนเองหรือประกาศที่ไม่ใช่ `available`
6. คำขอใหม่มีสถานะ `pending`
7. เจ้าของประกาศดูคำขอของประกาศตนเองเท่านั้น
8. เมื่ออนุมัติ คำขอเป็น `approved`, ประกาศเป็น `adopted` และคำขอ pending อื่นของสัตว์เดียวกันเป็น `rejected`
9. เมื่อปฏิเสธ คำขอเป็น `rejected` และประกาศยังคงสถานะเดิม

### FR-05 อีเมลแจ้งเตือน

เมื่อมี `RESEND_API_KEY` และอีเมลผู้รับ ระบบพยายามส่ง:

- แจ้งเจ้าของเมื่อมีคำขอใหม่
- ยืนยันผู้สมัครเมื่อส่งคำขอ
- แจ้งผลอนุมัติหรือปฏิเสธ

การส่งอีเมลไม่ควรทำให้คำขอหลักล้มเหลว หากบริการอีเมลไม่พร้อม ระบบบันทึกผลลง log

### FR-06 รายงานและผู้ดูแลระบบ

1. ผู้ใช้ที่ login แล้วรายงานประกาศได้ด้วยเหตุผลที่กำหนด: ข้อมูลไม่จริง เนื้อหาไม่เหมาะสม สงสัยหลอกลวง หรืออื่นๆ
2. ผู้ใช้หนึ่งคนมีรายงานที่ `pending` ต่อประกาศเดียวกันได้ครั้งละหนึ่งรายการ
3. ผู้ดูแลเห็นเฉพาะรายงาน `pending`
4. ผู้ดูแลทำได้สามแบบ: ดำเนินการแล้ว (`reviewed`), ยกเลิก (`dismissed`) หรือปิดประกาศ (`rejected` พร้อมบันทึก audit)

### FR-07 สถานะสุขภาพ

`GET /health` ต้องตอบ JSON `{"status":"ok"}` ด้วย HTTP 200 เมื่อแอปทำงาน

## 4. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน

| หมวด | ข้อกำหนด |
|---|---|
| ความปลอดภัย | ใช้ CSRF protection กับฟอร์ม, parameterized SQL, password hash และ session authorization |
| ความเป็นส่วนตัว | ไม่ log ค่า API key; ข้อมูลติดต่อคำขอควรเข้าถึงได้เฉพาะเจ้าของประกาศและผู้มีสิทธิ์ |
| ความถูกต้อง | ใช้ foreign key และ unique key ป้องกันข้อมูลกำพร้า/คำขอซ้ำ |
| ประสิทธิภาพ | query หน้าหลักต้องรองรับ filter และ pagination; production ใช้ Gunicorn |
| ความเข้ากันได้ | รองรับเบราว์เซอร์สมัยใหม่ที่รองรับ HTML5, Bootstrap 5 และ JavaScript พื้นฐาน |
| การจัดเก็บ | MySQL 8-compatible พร้อม charset `utf8mb4`; รูปใช้ Cloudinary หรือ local fallback |
| การดูแลระบบ | ค่า config ทั้งหมดที่เป็นความลับต้องมาจาก environment variables |

## 5. สถาปัตยกรรมและเทคโนโลยี

- **Presentation:** Jinja2 templates, Bootstrap 5.3.3, CSS และ JavaScript ใน `frontend/`
- **Application:** Flask 3, Python, `mysql.connector`, Flask-WTF CSRF
- **Data:** MySQL; schema อยู่ที่ `database/schema.sql` และ migration อยู่ที่ `database/migrations/`
- **Media:** Cloudinary (production ที่ตั้งค่าไว้) หรือ `frontend/static/uploads`
- **Email:** Resend Email API ผ่าน HTTPS
- **Deployment:** Gunicorn ตาม [Procfile](./Procfile)

## 6. โมเดลข้อมูล

ตารางหลัก:

- `users`: บัญชี ผู้สมัคร และบทบาท
- `pets`: ข้อมูลประกาศและสถานะ
- `pet_images`: URL รูปของสัตว์และรูปหลัก
- `adoption_requests`: คำขอและข้อมูลการติดต่อ/ที่พัก
- `admin_audit_logs`: ประวัติการอนุมัติ/ปฏิเสธหรือการจัดการประกาศโดย admin
- `reports`: รายงานประกาศและผลการตรวจสอบ

ความสัมพันธ์สำคัญ: `users 1:N pets`, `pets 1:N pet_images`, `pets N:N users` ผ่าน `adoption_requests`, และ `pets 1:N reports`

## 7. เส้นทาง HTTP หลัก

| Method | Path | สิทธิ์ | หน้าที่ |
|---|---|---|---|
| GET | `/` | สาธารณะ | หน้าหลัก/ค้นหา |
| GET/POST | `/register` | สาธารณะ | สมัครสมาชิก |
| GET/POST | `/login` | สาธารณะ | เข้าสู่ระบบ |
| POST | `/logout` | login | ออกจากระบบ |
| GET | `/pet/<id>` | สาธารณะ | รายละเอียด |
| GET/POST | `/add_pet` | login | เพิ่มประกาศ |
| GET/POST | `/edit_pet/<id>` | เจ้าของ | แก้ไขประกาศ |
| POST | `/delete_pet/<id>` | เจ้าของ | ลบประกาศ |
| POST | `/pet/<id>/adopt` | สาธารณะ | ส่งคำขอ |
| GET | `/adoption_requests` | login | ดูคำขอของเจ้าของ |
| POST | `/request/<id>/approve` | เจ้าของ | อนุมัติ |
| POST | `/request/<id>/reject` | เจ้าของ | ปฏิเสธ |
| POST | `/pet/<id>/report` | login | รายงาน |
| GET | `/admin` | admin | ศูนย์ผู้ดูแล |
| POST | `/admin/report/<id>/<action>` | admin | จัดการรายงาน |
| GET | `/health` | สาธารณะ | health check |

## 8. เงื่อนไขการติดตั้งและการยอมรับระบบ

1. ต้องมี Python ตาม runtime ที่โปรเจกต์ใช้งาน, MySQL และ dependency ใน [requirements.txt](./requirements.txt)
2. ต้องตั้งค่า `MYSQLHOST`, `MYSQLPORT`, `MYSQLUSER`, `MYSQLPASSWORD`, `MYSQLDATABASE`
3. production ต้องตั้ง `SECRET_KEY`
4. ระบบต้องสร้าง schema สำเร็จและเปิด `/health` ได้
5. ผู้ใช้ต้องสมัคร/login และสร้างประกาศได้
6. ผู้เยี่ยมชมต้องค้นหาและส่งคำขอได้
7. เจ้าของต้องอนุมัติ/ปฏิเสธคำขอได้ตามสิทธิ์
8. admin ต้องจัดการรายงานได้
